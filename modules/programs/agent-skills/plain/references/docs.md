# Docs and READMEs

The reader is looking for one thing and skimming until they find it.

- One job per page: a tutorial, a how-to, a reference or an explanation. Link between them instead of mixing.
- The first screen says what this is and when to use it. Install steps and history come later.
- Headers name what is under them, so a reader can jump. One level is enough for a page or two.
- Steps are a numbered list. Options, flags and fields are a table or a reference list with bold names.
- Explanation is prose: why it works this way, what was traded away.
- Describe only what exists today. Plans and history belong in issues and git.
- One fact, one home. Link to it rather than restating it.
- Literal words over figures of speech. If a sentence would fit any project, it says nothing about this one.

## Examples

Mannered to literal:

```text
Run the real thing and drive it by observation.
→ Each starts the real program and drives it with keys, screenshots and logs.
```

The first line sounds good and says nothing a reader can check. The second names what actually happens.

A description that shows off to one that informs:

```text
Sand marks the still lines of a vibrating plate: two diagonals and a ring of
small loops around a lit one.
→ Sand on a vibrating plate collects along the lines that stay still.
```

The reader can see the picture, so describing it again is noise. The one fact worth knowing is how it works.
